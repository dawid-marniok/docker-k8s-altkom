Kubernetes: droga zapytania i skąd biorą się pody

Trzy diagramy na przykładzie ToDos z lab09: którędy idzie zapytanie z przeglądarki do bazy, co się dzieje po kubectl apply i jak Deployment podmienia pody przy nowej wersji. Każdy diagram przejdziesz krok po kroku przyciskiem albo strzałkami na klawiaturze.

1. Od przeglądarki do bazy

Wpisujesz http://todos.localhost, a lista zadań przychodzi z MongoDB w podzie. Po drodze jest sześć obiektów Kubernetesa.

Najpierw spójrz na całość: zapytanie idzie górnym rzędem w prawo, potem dolnym w lewo, aż do dysku. Kliknij Start, żeby przejść po kolei.

Nazwy *.localhost zawsze wskazują na Twój komputer (127.0.0.1). Port 80 laptopa jest przekierowany do węzła klastra kind. To ustawienie extraPortMappings w setup/kind-config.yaml.

Traefik to Ingress Controller, czyli zwykła aplikacja w podzie, która przyjmuje ruch z zewnątrz. Sam obiekt Ingress to tylko reguła: „host todos.localhost, ścieżka / → Service web, port 80”. Bez kontrolera Ingress nic nie robi.

Pody mają zmienne IP: znikają i wracają z nowymi. Service daje stały adres (ClusterIP) i nazwę w DNS klastra. Które pody są „jego”, decyduje selector: app: web. Tutaj Service przyjmuje port 80 i kieruje na targetPort: 8080 kontenera.

Kubernetes sam utrzymuje listę IP podów, które pasują do selektora i są Ready. Pod, który nie przechodzi readinessProbe, wypada z listy i nie dostaje ruchu.

Pusta lista = Service bez ruchu. Najczęściej selektor nie pasuje do etykiet podów: kubectl get endpointslices -l kubernetes.io/service-name=web.

Ruch trafia do jednego z dwóch podów web. nginx zwraca stronę index.html. Zapytania pod /api/ przekazuje dalej, więc przeglądarka zna tylko jeden adres.

nginx ma w konfiguracji proxy_pass http://api:3000. Nazwa api to po prostu nazwa Service'u w tym samym namespace. Ten sam adres działał w Compose, bo tam api było nazwą usługi. Service rozkłada zapytania między dwa pody api.

Pod api bierze adres bazy ze zmiennej MONGO_URL=mongodb://mongo:27017 (z Secret api-secret). Znowu nazwa Service'u: mongo. Za nim jest jeden pod z MongoDB.

MongoDB zapisuje dane w /data/db, a tam jest zamontowany PersistentVolumeClaim. Usuń poda mongo: Deployment stworzy nowego, podepnie ten sam dysk i zadania zostaną.

Service nie jest pośrednikiem, przez który „przechodzi” ruch. To adres i nazwa. Ruch trafia prosto do IP poda z EndpointSlice. Dlatego gdy Service „nie działa”, sprawdzasz selektor, etykiety i gotowość podów, a nie sam Service.

2. Co się dzieje po kubectl apply

Od pliku YAML do działającego kontenera. Każdy element robi jedną rzecz i rozmawia tylko z API serverem.

Z lewej control plane, czyli „mózg” klastra. Pośrodku obiekty, które w nim zapisaliśmy. Z prawej węzły, na których naprawdę działają kontenery.

kubectl wysyła manifest do API servera. Ten sprawdza składnię i uprawnienia, a potem zapisuje Deployment w etcd. Na tym rola kubectl się kończy. Reszta dzieje się w klastrze, nawet gdy zamkniesz laptopa.

Kontroler Deploymentów widzi nowy Deployment i tworzy dla jego szablonu ReplicaSet. Końcówka nazwy to hash szablonu podów: każda zmiana w template (obraz, zmienne, zasoby) daje nowy ReplicaSet.

Kontroler ReplicaSetów porównuje: chcę 2, mam 0, więc tworzy 2 pody. Na razie nie mają węzła, ich status to Pending.

Scheduler szuka węzła dla każdego poda. Patrzy na requests (CPU, pamięć) i wolne zasoby, potem wpisuje węzeł do poda. Gdy żaden nie pasuje, pod zostaje w Pending, a przyczynę zobaczysz w Events: kubectl describe pod.

kubelet na węźle widzi przypisany pod, pobiera obraz i uruchamia kontener. Stan raportuje do API servera. Gdy readinessProbe przejdzie, pod jest Ready i trafia do EndpointSlice swojego Service'u.

Pętla kontrolna. Każdy kontroler w kółko porównuje stan zapisany z rzeczywistym i poprawia różnicę. Dlatego usunięty ręcznie pod wraca: ReplicaSet widzi 1 zamiast 2 i tworzy brakującego.

3. Rolling update: nowa wersja bez przerwy

kubectl set image deploy/api api=todos-api:1.1 przy replicas: 4 i domyślnej strategii: maxSurge: 25% (najwyżej 1 pod ponad plan) i maxUnavailable: 25% (najwyżej 1 pod mniej niż plan).

todos-api:1.0
nowy ReplicaSet
