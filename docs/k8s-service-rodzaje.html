Service w Kubernetesie: wszystkie rodzaje

Pody przychodzą i odchodzą, a ich IP się zmieniają. Service daje im stały adres i nazwę. Rodzaj Service decyduje, skąd da się do tego adresu dojść: tylko z klastra, z sieci węzłów czy z internetu.

Trzy podstawowe typy to warstwy

Każdy kolejny typ dokłada coś do poprzedniego. LoadBalancer ma w sobie NodePort, a NodePort ma w sobie ClusterIP.

Dwa pozostałe rodzaje to osobne przypadki: ExternalName to tylko alias DNS na adres spoza klastra, a Headless to ClusterIP bez wspólnego IP, w którym DNS zwraca adresy podów.

Trzy porty, które łatwo pomylić

Ruch przechodzi przez maksymalnie trzy numery portów. Tylko targetPort musi zgadzać się z aplikacją.

spec:
  type: NodePort
  selector:
    app: web
  ports:
    - port: 80
      targetPort: 8080
      nodePort: 30080

Pominiesz targetPort, to Kubernetes przyjmie wartość z port. Pominiesz nodePort, to wylosuje wolny z zakresu 30000–32767.

Najczęstszy błąd: targetPort wskazuje port, na którym aplikacja nie słucha. Service ma wtedy endpointy, ale połączenie jest odrzucane.

Każdy rodzaj osobno

Wybierz rodzaj. Kropka na diagramie pokazuje, którędy idzie ruch.

ClusterIP

Domyślny typ. Adres widoczny tylko wewnątrz klastra.

Service dostaje stały wirtualny IP i nazwę w DNS klastra. Ruch rozkłada na pody, które pasują do selector i są Ready. Z laptopa ani z internetu tego adresu nie widać.

Kiedy

  • komunikacja między usługami: web → api → mongo w ToDos
  • wszystko, co wystawiasz na zewnątrz przez Ingress

Sprawdź na kind

  • kubectl port-forward svc/web 8080:80
  • kubectl run klient --rm -it --image=busybox:1.37 -- wget -qO- http://web
apiVersion: v1
kind: Service
metadata:
  name: web
spec:
  # type: ClusterIP  (domyślnie)
  selector:
    app: web
  ports:
    - port: 80
      targetPort: 8080

NodePort

ClusterIP plus ten sam port otwarty na każdym węźle.

Kubernetes otwiera wybrany port (z zakresu 30000–32767) na wszystkich węzłach. Wejdziesz przez dowolny węzeł, nawet taki, na którym nie ma poda. kube-proxy przekaże ruch dalej.

Kiedy

  • szybki test z sieci, która widzi węzły
  • klastry on-premise z własnym load balancerem przed węzłami
  • rzadko na produkcji: nietypowe porty i adresy węzłów, które się zmieniają

Na kind

  • węzły to kontenery Dockera, więc z laptopa nie dojdziesz do IP-węzła:30080 bez extraPortMappings
  • test z wnętrza: kubectl get nodes -o wide, potem wget -qO- http://<INTERNAL-IP>:30080 z poda busybox
apiVersion: v1
kind: Service
metadata:
  name: web
spec:
  type: NodePort
  selector:
    app: web
  ports:
    - port: 80
      targetPort: 8080
      nodePort: 30080

LoadBalancer

NodePort plus zewnętrzny load balancer, którego dostarcza chmura.

Kubernetes prosi dostawcę chmury (AKS, EKS, GKE) o load balancer z publicznym IP. Ten rozsyła ruch na NodePort węzłów. Adres zobaczysz w kolumnie EXTERNAL-IP w kubectl get svc.

Kiedy

  • wystawienie pojedynczej usługi w chmurze, także ruchu innego niż HTTP (TCP, UDP)
  • wystawienie samego Ingress Controllera: jeden LoadBalancer i wiele aplikacji za Ingressem

Na kind

  • bez chmury EXTERNAL-IP zostaje w stanie <pending>; potrzeba dodatku cloud-provider-kind albo MetalLB
  • każdy LoadBalancer w chmurze to osobny, płatny zasób
apiVersion: v1
kind: Service
metadata:
  name: web
spec:
  type: LoadBalancer
  selector:
    app: web
  ports:
    - port: 80
      targetPort: 8080

Headless

ClusterIP bez wspólnego IP: DNS zwraca adresy samych podów.

Ustawiasz clusterIP: None. Service nie rozkłada ruchu. Zapytanie DNS o mongo zwraca listę IP gotowych podów i klient sam wybiera, z którym się połączyć. Ze StatefulSetem każdy pod ma też własną, stałą nazwę: mongo-0.mongo.

Kiedy

  • bazy danych i klastry (MongoDB replica set, Kafka, Elasticsearch), gdzie klient musi trafić do konkretnej instancji, np. primary
  • StatefulSet: serviceName wskazuje właśnie Service headless

Sprawdź na kind

  • kubectl run dns --rm -it --image=busybox:1.37 -- nslookup mongo: kilka adresów zamiast jednego
apiVersion: v1
kind: Service
metadata:
  name: mongo
spec:
  clusterIP: None
  selector:
    app: mongo
  ports:
    - port: 27017

ExternalName

Alias DNS na adres spoza klastra. Bez IP, bez podów i bez proxy.

DNS klastra odpowiada na pytanie o baza rekordem CNAME: db.firma.example.com. Aplikacja łączy się prosto z tym adresem. Kubernetes nie pośredniczy w ruchu i nie sprawdza, czy serwer działa.

Kiedy

  • aplikacja ma w konfiguracji krótką nazwę baza, a baza jest poza klastrem
  • przenosiny: dziś baza zewnętrzna, jutro pod w klastrze, a w aplikacji nic się nie zmienia

Uwaga

  • HTTPS i nagłówek Host dalej widzą baza, więc certyfikat serwera może nie pasować
  • pole ports nie ma znaczenia, port podaje aplikacja
apiVersion: v1
kind: Service
metadata:
  name: baza
spec:
  type: ExternalName
  externalName: db.firma.example.com

A Ingress? Ingress nie jest rodzajem Service. To reguły HTTP („host i ścieżka → Service”), które obsługuje Ingress Controller. Typowy układ w chmurze: jeden LoadBalancer przed Ingress Controllerem i wiele aplikacji jako ClusterIP za nim. Na naszym kind Traefik słucha wprost na porcie 80 węzła. Szczegóły: droga zapytania.
